01

What the view answers

  1. Did it work? Status pill, duration, and a step strip with counts in the header. No scrolling needed.
  2. If not, where and why? A failure banner names the failed step in plain English with the first line of its error, and opens that step on load.
  3. Where did the time go? The timeline. Bars on a shared clock show parallel branches, waits, and the step that held the run up. A one-line insight says it in words.
  4. What did a step get and return? The side panel, shaped by node type: request and response for HTTP, verdict and branch for a condition, prompt and result for agents and LLMs, command and exit code for CLI. Raw JSON stays one click away.
  5. What is it doing now? For a live run: a now line, a growing striped bar, elapsed time that ticks, and the steps still waiting with what they wait on.

02

Anatomy

1 · Run header Workflow name, run start, status pill, cause (schedule, manual, event), total duration (live while running), queued time, and the pinned version with a note when it is older than the live one. Actions: Cancel run while active, Back to editor.
2 · Banner Failed or timed out: the failed step, its error, and a Show step button. Succeeded: one insight line about where the time went. Running: hidden.
3 · Tabs and strip Timeline and Graph share one selection, so a step picked in one stays picked in the other. The strip is one segment per step, coloured by status, with counts.
4 · Timeline A Run row on top (queued, then running), then one row per node. Time axis is relative to when the run was created; hover shows wall-clock times.
5 · Step panel With no step picked: run overview (counts, trigger, version, error). With a step: summary, error, type-aware sections, raw input and output.

03

Timeline rules

  • Row order is graph order (topological, ties by start time), not event order. Rows must not jump while a run is live.
  • Linear scale, with zoom. Fit is the default. Short steps get a 3 px minimum bar and their duration as a label, so a 40 ms condition next to a 4 minute agent is still visible and clickable. ⌘-scroll zooms, the label column stays put.
  • Status is shape as well as colour. Done: solid bar. Failed: red bar with the error tag. Running: marching stripes to the now line. Skipped: a dashed ring dot and a sentence why, no bar. Pending: an empty ring and what it waits on.
  • Waits are drawn. A dotted line runs from the latest dependency's end to the step's start, so engine overhead and fan-in waits show up as gaps, not as nothing.
  • Critical path outlines the chain of steps that set the total duration and fades the rest. The same data drives the insight line in the banner.
  • Keyboard: ↑ ↓ move between steps, Esc clears the selection, F fits, G and T switch tabs.

04

Data we have, and what is missing

Everything in the mock above except attempts and agent phases comes from rows we already store: workflow_runs gives created, started and finished times, and workflow_run_steps gives one row per node with status, input, output, error, and start and finish. Node names and edges come from the run's pinned version.

05

Plan

  • v1, desktop only, no schema change. Run header, banner, Timeline and Graph tabs, type-aware step panel, derived skip reasons and waits. Replaces today's run strip and raw-JSON panel.
  • v2, engine events. workflow_run_events, retry attempts, agent phases, and the agent workspace link.
  • Later. A step strip on every row of the runs list, so a column of runs reads as a history at a glance; compare two runs on one axis.
